# 更新机制的 bug 报告

- 日期：2026-11-10
- 为什么有这个目录：AGENTS.md 规定默认在跑着的引擎上热改（`apply`），开发本身就是对热更新机制的测试。发现机制本身的问题，在这里留一份报告；做法见 `.claude/skills/rsinfer/SKILL.md`「在跑着的引擎上热改」。

## 报什么

热更新机制本身的问题，包括：
- 框架本体里的：变更协议（`core.change`）、单元运行时的加载 / 重载 / 撤销（`unit.runtime`）、快照和节点代理、数据通道在重载前后的行为；
- 控制面单元里的：计划不对（`core.deps`）、静态检查漏判或误判（`core.manifest`）、身份（`core.identity`）、控制接口（`core.api`）；
- 单元为了热更新声明或实现的东西出了错：`drain`、`on_config`、动作的 `prepare` / `commit` / `abort`、派生产物的重建。

不在这里报的：单元自己的功能 bug（直接修，或者写在单元自己的 README），以及 `doc/specs/empty-apply.md` 等规格里已经写明的正常行为（比如忙时被拒、改框架要求重启）。

## 怎么报

一个问题一个文件：`doc/framework-bugs/YYYY-MM-DD-<简短描述>.md`。同一个问题再碰到，在原文件里追加一条带日期的记录，不另开文件。

```markdown
# <一句话：什么变更之后出了什么问题>

- 日期：
- 报告人：（哪个 agent 或谁）
- 状态：未修 / 已修（PR #）/ 不是 bug（为什么）
- 引擎：怎么起的（命令、拓扑、平台），变更前的身份
- 变更：apply 的命令和参数；改了哪些文件、哪些配置键
- 现象：看到了什么（摘要或 `--json` 里相关的部分、日志的关键行）
- 期望：应该怎样，依据（规格的哪一节，或冷启动时的行为）
- 复现：最少的步骤；能写成测试的话，写在哪
- 绕过：怎么继续开发的（比如重启引擎，退回冷启动），后来还有没有碰到
```
