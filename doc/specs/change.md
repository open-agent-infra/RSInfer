# 规格：变更事务 `core.change`

- 类型：框架本体。跑在控制面进程。改了它要重启引擎。v0 用 Python；它只通过版本化消息和其他进程交互，以后可以换成 Rust。
- 公共约定见 [README.md](README.md)。

## 1. 职责

1. 接收 change-set：来自 agent 的 `apply`、配置修改、单元自己发起的内部变更（例如 EPLB）、启动（从空系统到某个身份）。
2. 按固定流程推进：静态检查 → 推导动作计划 → 准备 → epoch 边界暂停 → 执行 → 提交或回滚 → 恢复。
3. 作为两阶段提交的协调者。
4. 返回诚实的结果，并写事件日志。

## 2. 不负责

- 不判断要动哪些东西（问 `core.deps`）。
- 不执行具体动作（重载、重录 graph、refit、搬专家……都由参与进程里的单元执行）。
- 不做鉴权、不做策略钩子（v0 不做任何安全和权限）。

## 3. change-set

```python
class ChangeSet(msgspec.Struct):
    base: Identity                       # 起点身份
    files: dict[str, str | None]         # 路径 -> 新内容的 hash；None 表示删除
    config: dict[str, Any]               # 配置键 -> 新值
    deps: dict[str, str]                 # 依赖锁的变化
    topology: Topology | None            # 拓扑数据的变化（见 supervisor.md）
    artifacts: dict[str, str]            # 名称 -> 内容 hash
    source: Literal["apply", "config", "internal", "startup", "operator"]
    meta: ChangeMeta                     # 提交者（自报）、意图、证据链接
```

- 文件内容按 hash 存在内容寻址的 blob 存储里；unified diff 只用于展示。
- 候选身份 = f(起点身份, change-set)，必须是确定的。

## 4. 流程

### 4.1 状态机

```
RECEIVED → CHECKED → PLANNED → PREPARING → PREPARED → PAUSING → EXECUTING → COMMITTED
                │          │           │            │            │
                └──────────┴───────────┴────────────┴────────────┴──▶ ABORTING → ABORTED
```

同一时刻只处理一个 change-set，其余排队。排队规则见 4.5。

### 4.2 各阶段

1. **RECEIVED → CHECKED**：起点身份必须等于当前运行身份（内部变更除外，它以当前身份为起点）；调用 `core.manifest` 做静态检查；不通过就 `Failed`，什么都不动。
2. **CHECKED → PLANNED**：调用 `core.deps` 得到动作计划：每个参与进程要做什么、哪些动作会影响在途请求、哪些要重启进程或引擎。带 `--dry-run` 时到这里就返回计划。
3. **PLANNED → PREPARING**：让每台机器的节点代理拿到新内容并物化快照目录；向每个参与进程发 `Prepare`。参与进程做能提前做的事（装新增单元、后台重录 graph），**旧版本在此期间继续服务**（分片准备，见 4.6），全部做完后回 `Prepared` 或 `Failed`。
4. **PREPARED → PAUSING**：按需排空：通知持有受影响请求的单元，给它一个期限（默认 10 秒）；请求怎么处理（等它跑完、中止、退回排队）由那个单元按自己的策略决定，期限到了它报告剩下的请求各怎么处理了（2026-11-07，见 [state-changes.md](state-changes.md)）；向所有参与进程发 `Pause(epoch=E)`，要求在 epoch E 结束后停下。
   - epoch 编号：同一个调度域里只有一套编号，由调度方（领头的进程，`leads_epochs`）分配；worker 报告的是它实际做完的那一步的编号，重启后直接接入当前编号，不从零重新数。所以 E 对领头者和跟随者是同一轮工作。
   - 停下之前先收尾（2026-11-07）：循环单元（`proc.loop@1`）如果有 `quiesce()`，参与者先调它，让已经开始的步做完（GPU 上异步跑着的工作、重叠调度里提前发出的下一步），再停止调用 `step()`。`Paused` 报的是收尾以后做完的那一步。这样第 5 步卸掉的东西，不会还有在途的工作在用（GPU 探针 P1：真 graph 读到已释放的显存不报错，只会读到垃圾）。`quiesce()` 抛错时这次 `Pause` 失败（`host.quiesce_failed`），进程继续服务，协调者撤回变更。进程退出前、撤回失败只能停在暂停时，也先收尾。
   - 跟随者要等的 epoch E，可能只有收尾才能做完：领头者停在 E 以后不再发下一步，E 这一步还在途（2026-11-07，PR #18 评审）。所以先收尾，再看做完的 epoch 有没有到 E。没到就接着走，下一个安全点再收尾、再看，到了才回 `Paused`。还没做完任何一步不算到；没有循环单元的进程不编 epoch，直接停。
   - 退出前收尾失败：GPU 上可能还有工作在用单元的显存，所以不卸单元，进程以退出码 4（`EXIT_QUIESCE_FAILED`）退出，资源随进程结束释放。`paused` 不能当作“收尾已成功”的依据（撤回失败时，收尾失败也会置上它），宿主另记 `settled`：上次成功收尾以后还没有开始新的步。
5. **PAUSING → EXECUTING**：所有参与进程都停下后，发 `Execute`：执行推迟的动作（重载修改过的单元、暂停期内重建派生产物、状态动作）。参与者此时切换到新身份的快照目录：就算动作计划里没有重载，也要切换代码来源，并让准备阶段装上的单元转正。需要重启或新建的进程交给 `core.supervisor`，它们**一启动就处于暂停**，等第 6 步的 `Resume`。
6. **EXECUTING → COMMITTED**：所有参与进程回 `Executed` 后，协调者**先把“决定提交”写进事件日志**，再分两轮确认：
   - **`Commit` / `Committed`**：参与者记下新身份、运行单元的 commit 钩子，但**仍然暂停**；
   - **`Resume` / `Resumed`**：所有参与者都回了 `Committed` 之后，才向它们和新启动的进程发 `Resume`，它们这时才恢复服务。
   - 这样，任何时刻都不会有一个进程已经用新版本服务、另一个进程却还没答应提交。确认的重试和上限见 4.7，确认不了时见 4.8。
7. **任一步失败 → ABORTING**：协调者先把“决定撤回”写进事件日志，再向收到过 `Prepare` 的参与进程发 `Abort`，它们各自回滚（单元运行时的回滚见 [unit-runtime.md](unit-runtime.md) 6.2），然后恢复服务；身份不变。这个变更停掉的进程按原来的规格重新启动，拓扑恢复成变更开始时的样子。

### 4.3 协议消息

| 消息 | 方向 | 内容 |
|---|---|---|
| `Prepare` | 协调者 → 参与者 | change-set id、给这个进程的动作片段、新快照的身份 |
| `Prepared` / `Failed` | 参与者 → 协调者 | 诊断 |
| `Pause` | 协调者 → 参与者 | 在哪个 epoch 之后停下 |
| `Paused` | 参与者 → 协调者 | 实际停在的 epoch |
| `Execute` / `Executed` | 双向 | 动作执行结果 |
| `Commit` / `Committed` | 协调者 → 参与者 / 回复 | 记下新身份，仍然暂停；`Committed` 带 change id 和身份，协调者逐项核对（`change.commit@2`） |
| `Resume` / `Resumed` | 协调者 → 参与者 / 回复 | 所有参与者都已提交，恢复服务；`Resumed` 带当前身份和这个进程还在用的快照（节点代理不能清理它们） |
| `Abort` / `Resumed` | 协调者 → 参与者 / 回复 | 回滚并恢复服务；已经提交的参与者拒绝 `Abort`（`change.already_committed`） |
| `KeepAlive` / `Alive` | 协调者 → 参与者 / 回复 | 续租：协调者还活着，只是在忙（见 4.7） |
| `QueryDecision` / `Decision` | 参与者 → 协调者 / 回复 | 参与者询问某个变更的结果：`commit`、`abort`、`pending`（还没决定）、`unknown`（协调者不知道这个变更） |

- 参与者按 `ProcId` 寻址，可以跨机（P7）。
- 每条消息都带 change-set id，参与者对重复消息和迟到的消息幂等（[ipc.md](ipc.md) 第 4 节）。
- `Commit` 的语义改过（先确认、后恢复），框架进程要一起更新，不能新旧混用。
- 参与者失去协调者时怎么办，见 4.7（已确认）。

### 4.4 失败的边界

- 控制面进程崩溃 = 引擎重启。事件日志在磁盘上，不丢。
- 某个参与进程崩溃：整体 abort；由 `core.supervisor` 按拓扑决定要不要重建它。
- 决定提交以后，有参与者确认不了 `Commit` 或 `Resume`（4.7 第 5 条）：不能报告“提交成功”，按 4.8 进入恢复。
- `core.supervisor` 判定某个进程丢失，只是故障检测的结论，**不能当成“它已经停止服务”或“它已经提交”的证据**。

### 4.5 排队规则（已确认）

1. **不抢占**：正在走流程的 change-set 不会被打断，后来的都排队。
2. **优先级**：故障处理（进程丢失、机器丢失）> 内部变更 > agent 的 apply 和其他来源。内部变更优先，是因为它短（例如 EPLB 重排不重录、不排空），而且时效性强（负载统计放久了就过时）。
3. **防饿死**：有 apply 在等时，内部变更最多连续插一次队。
4. **内部变更可以丢弃，apply 永远不丢**：内部变更带着“在哪个身份下算出来的”（`computed_under`）。轮到它执行时，如果当前身份已经不是 `computed_under`，就直接丢弃并记一条事件；发起它的单元下个周期重新算。apply 代表 agent 的意图，只会成功、失败或被拒，不会被静默丢弃。

### 4.6 分片准备（已确认）

准备阶段的目标是**旧版本继续服务，新版本在旁边准备**。例如换了一个 decode kernel，新 graph 在第二套 buffer 里录，旧 graph 照常服务，最后在 epoch 边界一瞬间切过去。

做法是不用多线程，而是**分片**：
- 单元参与变更的准备钩子 `prepare(args)` 可以一次做完（返回 `None`），也可以返回一个迭代器，**每次 `next()` 做一小片**，例如录一个 batch 档位的 graph。
- 参与者在每个安全点（两步之间）推进每个未完成的准备一片，然后主循环照常跑下一步。所有准备都做完后，才回 `Prepared`。任何一片抛错，就撤回已经准备的东西，回 `Failed`。
- 协调者等 `Prepared` 的时限是配置项 `change.prepare_timeout_s`（默认 600 秒），超时就整体 abort。
- 协调者等 `Executed` 的时限是 `change.execute_timeout_s`（默认 3600 秒，2026-11-12），不是任何调用都用的 `supervisor.rpc_timeout_s`（30 秒）：暂停期内的重载可能要读 checkpoint、录 CUDA graph（从 `holder.sleep` 醒来、改了权重存储），64 层模型在 SM100 上约 30 秒。执行超时以后发的 `Abort` 也等这么久：参与者只有 Execute 返回以后才读得到它，然后还要重载回去。
- 每个安全点先读完 socket 里的控制消息（包括协调者的心跳 `KeepAlive`，续上租约），再检查租约是否到期，最后才推进本轮分片（2026-11-27，修正 2026-11-07 的累加延期做法）：这样单个分片比租约长时，期间排在 socket 里的心跳会在下一个安全点先被读到，不会误判协调者失联；而协调者真失联时，不会因为每次分片都把租约往后延而把失联检测时间成倍拉长，仍按真实的 `change.coordinator_timeout_s` 撤回。
- **退路**：做不到分片的准备（实现太复杂，或者必须独占）就一次做完。这时准备期间主循环不跑步，停服时长等于准备时长，诊断里要写明。
- 准备期间不能改变正在服务的东西：新增单元可以装上（[unit-runtime.md](unit-runtime.md) 6.3），新 graph 只能录在第二套 buffer 里；修改已有模块、切换 graph 都留到暂停期内。
- **装新单元也分片**（2026-11-07）：第一片检查新单元、声明它们的配置键，不跑单元代码；之后每片装一个单元，两片之间主循环照常跑步、回请求。全部装好、都 ACTIVE 才算这一项准备完；有一个失败就全部撤掉。新单元自己的准备动作，在它装好以后再开始，也按它自己的分片走。哪些动作推迟到安全点、在重载出来的新实例上准备，也等装完再按实际的依赖图算：新单元用到了要重载的单元的服务，重载会把它一起重建，它的动作就要推迟。（以前是一次装完，报 `change.prepare_one_shot`；单元构造函数慢的时候，停服时长就是所有新单元构造时间之和。）

- **单元的构建步骤**（2026-11-11）：清单的 `[unit] build = "模块:函数"` 写着这个单元有什么慢的东西要先做出来（比如把原生扩展编译进缓存）。变更重载这个单元、或者把它加进一个已在服务的进程时，参与者在准备阶段先跑它：用这次变更的代码（候选快照，`PYTHONPATH` 指向它）另起一个进程，每片只看一眼它跑完没有。所以它跑多久，旧版本就照常服务多久，它不占这个进程的 GIL，暂停期内的加载找到的是做好的东西。退出码不是 0 就让变更失败，这时什么都还没暂停。撤回时停掉还在跑的构建（2026-11-12，Codex 的审查）：它在自己的会话里，先给整个会话发 SIGTERM，构建进程把它变成 `SystemExit`，清理照常跑（PyTorch 的扩展构建删掉它在构建目录上的锁文件、杀掉它等的 `ninja`）；`change.build_stop_grace_s`（默认 5 秒）以后会话里还剩的进程全部 SIGKILL。跑变更的进程结束时（不管怎么结束）构建进程收到 SIGTERM（`PR_SET_PDEATHSIG`）。这时没有谁再从外面停它的会话，它自己来（2026-11-12 第二轮，Codex）：先给会话里其余的进程发 SIGTERM，再做自己的清理，`change.build_stop_grace_s` 以后会话里还剩的全部 SIGKILL。构建进程跑的是 `core.change.build` 这个模块。进程停机时也先停掉它。进程刚起来时（启动）不跑：那时还没有服务，加载自己会做。以前改了 `kernels.cuda` 的 C++ 源码，编译发生在暂停期内的重载里，超过执行时限（30 秒），变更被撤回，引擎回了约一分钟的 503。

参照：sglang 的 EPLB 搬专家权重，就是在两次前向之间一层一层地搬（`expert_location_updater.py`）。

### 4.7 参与者失去协调者时（已确认）

**为什么要规定这一条**：一个参与者回了 `Prepared` 以后，就是答应了“协调者说提交我就提交”；最终结果只有协调者知道。如果它因为一段时间没收到消息就自己回滚，而协调者其实还活着、只是在忙（比如在重启另一个进程），最后就会出现“协调者报告提交成功，一部分参与者却已经退回旧版本”，同一个引擎里同时跑着两个版本，而且没有任何报错。

规则：
1. **租约**：参与者收到协调者的任何消息，都把“协调者丢失”的计时器（`change.coordinator_timeout_s`，默认 60 秒）重新开始计时。
2. **心跳**：从发出 `Prepare` 起到变更结束，协调者每隔 `change.keepalive_interval_s`（默认 10 秒）给所有参与者发一次 `KeepAlive`，尤其是在执行、重启进程这类长阶段里。
3. **还没回 `Prepared` 的参与者**（还在准备）：计时器到点，可以自己撤回准备、恢复服务，因为它还没答应任何事。
4. **已经回了 `Prepared` 的参与者**：计时器到点，**不能直接回滚**，要先发 `QueryDecision` 问协调者：
   - 回答 `abort`：回滚；
   - 回答 `pending`：协调者还活着，计时器重新开始；
   - 还没执行（没收到 `Execute`）时，回答 `unknown` 或者问不到：回滚并恢复服务，报告诊断。协调者只有在所有参与者都回了 `Executed` 之后才会决定提交，所以这时回滚是安全的；
   - **已经执行完**时，回答 `commit`：照着提交，但**仍然暂停**，等 `Resume`；
   - **已经执行完**时，回答 `unknown` 或者问不到：**保持暂停**，报告诊断（`change.in_doubt`），计时器重新开始。它可能已经处在一个“决定提交”的变更里，自己回滚就会造成版本分裂；
   - 已经提交、在等 `Resume` 的参与者：计时器到点只报告诊断，继续等。
5. **确认有上限**：`Commit` 和 `Resume` 各自最多尝试 `change.commit_attempts` 次（默认 3 次，间隔 `change.commit_retry_interval_s`），两轮加起来不超过 `change.commit_ack_timeout_s`（默认 120 秒，包括卡住的 RPC）。**次数用完或者时间到，都会结束确认**。
   - 设上限的原因：“进程还活着但不响应”（被暂停、NCCL 卡死、某个单元的 `step()` 卡住）不会被判定为丢失；没有上限的话，协调者会永远卡在这里，整个变更队列（包括故障处理）都被堵住。
   - 回执要逐项核对：消息类型、change id、身份都对得上才算确认；`rolled_back=True` 的 `Resumed` 不算。
6. 协调者发 `Commit` 或 `Abort` 之前，先把决定写进事件日志；`QueryDecision` 按事件日志和当前进行中的变更回答。

### 4.8 提交确认不了时

决定提交以后，只要有参与者在 4.7 第 5 条的上限内没有确认 `Commit` 或 `Resume`：
- 结果状态为 `failed`，诊断码 `change.recovery_required`。诊断里写明：**已经决定提交到哪个身份、哪些进程没有确认、需要恢复**。这不表示已经回滚。
- 协调者的当前身份和结果的 `new_identity` 都是决定提交的身份；`old_identity` 仍是变更前的身份。
- 没确认的参与者保持暂停；不发 `Abort`；不自动重启某个参与者并假定它已经被安全替换（它可能只是失联，还在服务旧版本）。
- **冻结**：之后的普通变更一律拒绝（`change.recovery_required`），直到恢复。不能只建议调用方换一个起点身份接着提交。
- **恢复方式是整体重启引擎**。

**决定**（发起人，2026-11-07）：不做“恢复同一个事务”。到了这种极端情况就 fail fast，整体重启引擎，不再写重启之外的恢复逻辑。此前记的“长期方向”（按持久化的决定重试补齐 `Commit` / `Resume`、确认旧进程停止后局部替换）作废。

## 5. 结果

```python
class ChangeResult(msgspec.Struct):
    status: Literal["committed", "aborted", "failed", "planned"]  # planned 只用于 dry-run
    old_identity: Identity
    new_identity: Identity | None
    plan: ActionPlan             # 实际执行的动作计划
    timings: dict[str, float]    # 各阶段耗时，包括排空耗时
    drain_outcomes: dict[str, int]  # 排空期限到时，持有请求的单元按自己的策略怎么处理了剩下的请求，各多少个（如 {"aborted": 2, "requeued": 5}）
    restarted: list[ProcId]
    diagnostics: list[Diagnostic]
```

结果同时写入事件日志，见 5.1。

### 5.1 事件日志和 blob 存储（已确认）

sqlite 只存索引和摘要，不存 patch 的内容：

| 放哪里 | 存什么 |
|---|---|
| **blob 存储**（控制面本机目录，按内容 hash 寻址） | 文件内容；change-set 本身（“路径 → 内容 hash”的清单）；每个身份的完整文件清单；大的产物 |
| **sqlite 事件日志**（控制面本机） | 每条变更的编号、来源、状态、起点和新身份、状态版本、change-set 的 hash（指向 blob）、配置的改动、实际执行的动作计划、各阶段耗时、诊断 |
| **按需生成，不存** | 给人审查的 unified diff：从两个身份的 blob 现算 |

- 同一份文件内容不管出现在多少个 change-set 里只存一份；节点代理物化快照时也从这个 blob 存储按 hash 拉文件，不另存一份。
- blob 按保留策略清理（保留当前身份、正在准备的身份、最近若干个身份引用的 blob，以及排队中的变更要用的 blob；保留数是配置项 `change.blob_retention`，默认 20）。事件记录本身永远保留；内容被清理的记录标明“内容已清理”。
- **宽限期**：agent 是先上传 blob、后提交 change-set 的，中间这段时间 blob 还没被任何变更引用。所以只清理存在时间超过 `change.blob_grace_s`（默认 3600 秒）的 blob。有了宽限期，清理就可以在每次变更结束后、或者空闲时自动跑。
- **什么时候清理**（2026-11-07）：在两次变更之间跑，最多每 `change.blob_prune_interval_s`（默认 300 秒）一次，不再每次变更后全量扫一遍。每批最多删 `change.blob_prune_batch`（默认 500）个，批与批之间让出事件循环，RPC 和心跳照常处理；有变更在排队就先让它跑，剩下的下一轮接着清。每批都重新算一遍要保留什么。已经标为“内容已清理”的记录不再重复检查（删掉的 blob 不会以同一个 hash 回来）。
- 引擎不承担完整历史的永久保存；需要的话由 RSI 平面的谱系（bare git 仓库）负责。

## 6. 内部变更入口

单元（例如调度宿主里的 EPLB 策略）通过控制面提供的服务提交 change-set，`source = "internal"`。走同一条流程（epoch 边界、两阶段提交），不同之处如下（已确认）：

1. **只改状态内容的内部变更不产生新身份。** 例如 EPLB 重排只改专家放置表和专家槽位里的内容，这和 KV cache 里存了什么一样，属于状态内容，不属于“系统是什么”（参照模式下换放置位置，输出不变）。事件日志里记成“状态版本 + 1”，身份不变。这样它不会让排在后面的 apply 因为起点对不上而被拒。
2. 内部变更必须带 `computed_under`（算出它时的身份），过时就丢弃（4.5 第 4 条）。不带的，在 RECEIVED 阶段直接拒绝。
3. 会改变身份的内部变更（如果以后有）照常产生新身份，和 apply 一样处理。
4. 标为“只改状态内容”的 change-set 不能带 `files`、`config`、`deps`、`topology`、`artifacts` 的改动，否则内容变了身份却不变，身份就不可信了；带了的在 RECEIVED 阶段直接拒绝。
5. 结果里的 `old_identity` 是提交前的运行身份，不是 change-set 里自报的 `base`（内部变更不检查 `base`）。

## 7. 验收测试（阶段 1）

1. 每个场景（modules.html 的 9 个）走完整流程，结果和事件日志正确。
2. 原子性：在任一阶段、任一参与者注入失败，所有参与者回滚，身份不变，服务继续。
3. 失去协调者：
   - 还在准备的参与者，计时器到点后自行撤回；
   - 已经回了 `Prepared`、还没执行的参与者，计时器到点后先问协调者，按回答回滚或继续等；问不到时才自行回滚；
   - 已经执行完的参与者，问到 `commit` 就提交但保持暂停；问不到或 `unknown` 时保持暂停，不回滚。
4. dry-run 的计划和实际执行的计划完全一致。
5. 排空：不影响在途请求的改动不排空；期限到了，由持有请求的单元按自己的策略处理剩下的请求，结果记进 `drain_outcomes`。
6. 一步之内只用一个版本：暂停前后的每一步，所有参与进程报告的身份一致。
7. 两个假主机：参与者分在两台“主机”上，以上全部成立。
8. 排队：同时到达的故障处理、内部变更、apply 按优先级执行；有 apply 在等时内部变更最多连续插一次队；正在走流程的变更不被打断。
9. 过时丢弃：apply 先提交改变了身份后，排在后面、`computed_under` 是旧身份的内部变更被丢弃并记事件；apply 永远不被丢弃。
10. 身份中立：只改状态内容的内部变更提交后，身份不变、状态版本加 1，排在后面的 apply 不会因为起点不符被拒。
11. 事件日志：sqlite 里没有文件内容；从事件记录和 blob 存储能重建 change-set 和 diff；blob 被清理后记录标明“内容已清理”。
12. 长执行阶段：执行阶段（例如重启另一个进程）比 `change.coordinator_timeout_s` 长时，有心跳的情况下所有参与者都不回滚，最后全部提交到新身份。没有心跳、执行完的参与者问不到协调者时保持暂停，最后同样提交，不重启。
13. 不报假成功：`Commit` 或 `Resume` 的请求、回执丢失时会重试；一直确认不了时结果为 `failed/change.recovery_required`，没有任何进程在所有参与者确认 `Commit` 之前恢复服务，之后的变更被拒绝。新启动、重启的进程也要等 `Resume`。**任何情况下，结果为 `committed` 时，所有参与者的身份都等于新身份。**
14. 分片准备：一个分成多片的准备进行期间，主循环照常跑步、旧版本照常服务；准备完成后才进入暂停。任何一片抛错，整体 abort 且没有残留。
15. 准备的退路：不分片的准备一次做完，期间不跑步，诊断里写明停服时长。
16. 卡死的参与者：`Commit` 前让一个参与者卡死（例如 SIGSTOP），协调者在 `change.commit_ack_timeout_s` 之内结束确认，结果为 `failed/change.recovery_required`，不会一直卡住；其他参与者保持暂停，排在后面的变更被拒绝（4.8）。
17. blob 宽限期：刚上传、还没被任何变更引用、存在时间不到 `change.blob_grace_s` 的 blob 不会被清理。
