# Mooncake 缓存与 PD 分离（2026-11-26）

## 目标与版本

以 `bd26c7e1554211a578e733f7e2fc59feb3a21452` 为基线，分两个可审阅提交：
先交付 Mooncake Store 缓存，再交付依赖它的 PD 路由。用户在实现、自审、实验之后审阅；本任务不推送远端、不创建 PR。

## 方案

参考 SGLang `661d9b3fb4005d622c8fcbb919281f5221fed540` 的 HiCache Store 接口、辅助状态一起传输及 PD 完成确认原则。
首版通过 Mooncake Store 的主机内存对象交接，选择容易验证正确性的同步复制；直接 GPU Transfer Engine/RDMA、异步分层预取属于后续性能工作。

缓存由独立 `state.cache` Unit 提供服务。前端异步查询已发布的提示词前缀，调度器在私有页和状态槽上预留空间，worker 验证快照后恢复，并从该位置继续计算。每个快照同时包含所有 KV 和 GDN 张量，不能只传 KV。
本地 radix 与远程快照的所有权不同，首版远程模式使用现有无缓存联合分配器；不修改框架本体。新消息字段有关闭功能的默认值，旧消息仍可读取，功能启用/变更经过现有排空流程。

只支持经验证的单 rank Qwen 混合模型、非投机且无调度重叠；其他组合显式拒绝。普通缓存保存完整页边界的前缀，至少留一个 token 重算。PD 使用独立请求键交接，decode 重算末尾一个 token，从而无需跨实例迁移采样器、detokenizer 和首 token 输出状态。

键隔离模型权重版本、配置、状态布局和实现版本。对象完整写入后才可查询；恢复前验证所有张量与长度，不能部分验证部分写入。普通缓存读写失败不制造假命中，恢复阶段丢失对象明确结束该请求，其他请求继续服务。原生 I/O 放到有期限、可回收的专属子进程，防止 Store 故障挂住控制面。

## 实施与验收

1. 远程独立 CPU 环境，生成小型四层混合模型，启动基线引擎并记录输出。
2. 新增缓存服务、快照编码、跨单元数据、前端查找、调度与 executor 恢复/发布；在常驻引擎 apply 后探测。
3. 留下状态往返、损坏/失配拒绝、故障隔离、跨进程实际缓存命中回归；运行 strict pyright 和完整默认 pytest，自审后提交缓存功能。
4. 增加 PD 实例角色、就绪交接和路由入口，覆盖请求成功、失败、取消及清理；重复自审和提交前检查，另一个提交。
5. CPU 与单张 4090 D 上进行冷/热缓存、两个独立 P/D 实例的确定性输出对照，记录真实传输和命中，测试热改与冷启动一致性。
6. 交付中文说明、准确环境/命令/日志、两个提交与补丁；不将单卡 TCP 实验表述为跨机 RDMA 或生产吞吐证明。

## 设计自审

状态完整性由统一声明和实际绑定共同检查；内存始终由目标 ledger 分配，远端不指定本地地址。缓存是可失效的外部数据，读到的字节不作为代码加载。两项功能关闭时保留既有行为。实验采用可容纳的确定性小权重，测试系统正确性，不据此判断模型质量。
